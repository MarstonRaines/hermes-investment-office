## 执行摘要

### 1.1 TS-08 是什么

TS-08 把 ts01–ts07 中分散的验收条款（ts01 八项验收问题、ts02 §15 验收与架构测试挂钩、ts03 §12 验收与 Pydantic 校验清单、ts04 §10 十一项机器验证、ts05 §10 A1–A10、ts06 §10 验收表与各引擎黄金值要求、ts07 §7 测试与验收）收敛为一份**分层测试矩阵**。它的本质是：

> **测试是施工纪律的机器化（冻结规范 §46 首句："施工纪律是文字约束，必须由机器保障"）。**

因此 TS-08 的三条主线是：

1. **分层**：单元 / 黄金值 / 集成 / 架构 / 契约 / 验收六层，每层有独立目录、命名、fixtures 与失败门禁（§2）；
2. **机器化**：冻结规范 §46 的七项架构测试逐项展开为可执行测试清单（§3），ts06 的黄金值要求逐引擎展开为黄金值矩阵（§4），ts07 的 18 错误码、ts04 的 freshness/quality/provenance 契约逐条展开为契约测试（§5）；
3. **里程碑化**：每个 Milestone 验收 = **fresh test 全绿**（冻结规范 §48.13），TS-08.7 给出 M0→M7 每个里程碑必须全绿的测试组映射，与冻结规范 §47 逐条对应。

### 1.2 关键设计决策（TS-08 冻结）

| # | 决策 | 说明 |
|---|---|---|
| K1 | **六层测试模型** | `unit（领域单元）→ golden（引擎黄金值）→ contract（数据/接口契约）→ integration（DB/MCP 集成）→ architecture（§46 七项）→ acceptance（Milestone）`；层次间的依赖是单向的，高层失败必然可回溯到低层某用例 |
| K2 | **架构测试与黄金值是两条独立的硬门槛** | 架构测试管"代码结构/边界不违规"（§46 七项逐项机器断言）；黄金值管"确定性计算数值正确"（ts06 E8）；两者在 CI 中都不可跳过、不可降级 |
| K3 | **每个 Milestone 验收 = fresh test 全绿** | fresh test 语义：在干净的 CI 环境中从零执行 架构→单元→黄金→契约→集成 全量重跑（§10.1），不是"增量通过"；冻结规范 §48.13 机器化 |
| K4 | **黄金值输入只允许由 ts06 契约构造** | 任何黄金值场景的输入（事实值 + 假设 + 参数 + engine_version + as_of）必须能在 ts06 的输入契约中找到构造方法，禁止发明契约外输入（如未冻结的 metric_code、未注册的 model_type） |
| K5 | **测试 ID 全局唯一、分层可排序** | `<层>-<域>-<序号>`（ARCH/GOLD/CTR/STM/DQ/ACC）；同一测试 ID 的输入构造与期望断言在矩阵表中给出，施工时逐条落 pytest |
| K6 | **时间冻结（freezegun）+ 定点语义** | PIT/freshness/黄金值测试必须冻结时间（freezegun）以消除"今天"漂移；金额断言基于 PG `NUMERIC` 定点语义（ts02 §1.2），分析层 DOUBLE 计算通过容差测试兜底，但黄金值断言必须基于定点结果（ts06 §2.6） |

## 2. 测试金字塔与分层定义（TS-08.1）

### 2.1 分层模型

```text
                 ▲  acceptance（Milestone 验收映射）
                / \     -- ACC-*：里程碑 gate，fresh test 全绿
               /   \
              /     \
    ┌─────────────────────────┐
    │  architecture（§46 七项） │    -- ARCH-*：代码结构/边界/白名单，静态 + 动态
    ├─────────────────────────┤
    │  integration（DB/MCP）   │    -- INT-*：真实 PG + DuckDB + MCP 端到端
    ├─────────────────────────┤
    │  contract（数据/接口）    │    -- CTR-*：Pydantic/Parquet/错误码/freshness/provenance
    ├─────────────────────────┤
    │  golden（引擎确定性）     │    -- GOLD-*：输入表 → 期望输出（定点语义）
    ├─────────────────────────┤
    │  unit（领域单元/状态机）   │    -- STM-*/DQ-*/枚举/校验：无外部依赖，纯内存
    └─────────────────────────┘
```

| 层 | 职责 | 依赖外部资源 | 失败门禁（§10.3） |
|---|---|---|---|
| **单元（unit）** | 状态机迁移、枚举合法值、缺口语义、typed domain error、纯函数（冲突裁决、quality_score 计算） | 无（纯内存 + 固定 fixture） | 每 PR 必须全绿 |
| **黄金值（golden）** | 六引擎每个计算路径的 `输入表 → 期望输出`（定点断言） | 无（输入表直接注入引擎核心函数） | 版本发布门槛（ts06 E8）：黄金值回归失败 = 不得发布 |
| **契约（contract）** | Pydantic 校验、Parquet schema 版本化、四元组重建、freshness 状态机、18 错误码、provenance 强制、fallback 记录 | schema 文件（`schema.json`/`attention_rules.yaml`/golden 数据文件） | 每 PR 必须全绿 |
| **集成（integration）** | 真实 PostgreSQL（测试库）+ DuckDB + MCP 端点端到端；PIT 查询、并发 409、append-only 触发器、审计联动 | 测试数据库容器（docker-compose test profile） | 每 Milestone 前必须全绿（可在 PR 级按标签选择性运行） |
| **架构（architecture）** | 冻结规范 §46 七项 + 补充（§3 全清单） | 源码树 + registry.py + 配置文件 | **任何 PR 不可跳过**（架构违规 = 合入门槛） |
| **验收（acceptance）** | Milestone 验收映射（§8）：把 §47 的验收条目映射到测试组 | 全部上层 | 每 Milestone 结束 fresh test 全绿 |

## 3. 架构测试矩阵（TS-08.2，冻结规范 §46 七项逐一展开）

> 本矩阵是**冻结规范 §46 的逐条落地**。每个小节首行给出 §46 原文条款号与原文；测试 ID 覆盖"静态规则 + 动态断言"两种形态。**架构测试是任何 PR 的合入门槛，不可跳过（§10.3）。**

### 3.1 §46.1 模块依赖方向（ARCH-DEP）

> §46.1 原文："模块依赖方向：禁止领域模块反向依赖（如 portfolio → providers、valuation → market_data 的内部实现）；使用 import-linter / pytest-arch 或等效机制"

**import-linter 规则清单（架构测试的机器输入，冻结）：**

| 规则名 | 依赖方向（依赖方 → 被依赖方） | 依据 |
|---|---|---|
| `D1 layers` | `api`/`mcp` → `service` → `repository` → 领域模块；任何一层不得反向 | ts03 §6.1、冻结规范 §9 |
| `D2 domain_independent` | `instruments`、`jobs`、`calendar` 为根模块，**不得依赖任何其他领域模块** | ts03 §6.2 归属表 |
| `D3 providers_leaf` | `providers` 只允许被 `market_data`/`fundamentals`/`etf`/`fx` 数据服务（经 Data Gateway）调用；**`valuation`/`portfolio`/`risk` 引擎禁止 import `providers.*`** | ts05 §P1、ts06 §2.2.1 |
| `D4 engine_readonly` | 引擎模块（`valuation`/`etf`/`portfolio`/`risk`/`fx`/`briefing`）禁止 import 上游事实表的 repository（`market_data`/`fundamentals`/`etf` 数据写入侧） | ts06 §1.2 边界纪律 |
| `D5 no_thesis_to_portfolio` | `thesis` 禁止依赖 `portfolio`；`portfolio` 可依赖 `thesis`（单向，`trade_proposals.thesis_revision_id`） | ts03 §6.1 规则 2 |
| `D6 research_support` | `research` 禁止依赖 `valuation`/`portfolio`（Workspace 是支持域，不拥有投资状态） | ts01 §1.1 |
| `D7 api_mcp_thin` | `api`/`mcp` 只允许依赖各领域的 `schemas` 与 `service` 门面，禁止 import `models`/`repository` 直读表 | ts03 §6.1.3、ts07 §7.1 |
| `D8 common_single` | 所有模块只允许 import `app.common.*`（enums/base/types/schemas），禁止 common 反向依赖任何领域模块 | ts03 §3–§4 |
| `D9 dashboard_isolated` | `dashboard` 不依赖任何领域模块内部实现（只经 Backend API） | §46.3、冻结规范 §40 |
| `D10 no_cross_model_import` | 业务代码禁止从 `app.models`（中央聚合，§6.5）import 模型类；只能从所属模块 `__init__.py` import | ts03 §6.5 |

## 6. 状态机测试矩阵（TS-08.5，ts01 §4 落地）

> 每张表给出 **transition table**（合法迁移）+ **非法迁移必须返回 typed domain error** 的测试（ts01 §4 验收标准："针对每个状态机编写 transition matrix tests；非法迁移必须返回 typed domain error，而不是任意 `status=...` 更新"）。状态迁移一律用条件 UPDATE（`WHERE status=<期望当前>`，影响行数 0 → 409 typed error，ts02 §12.3）。

### 6.1 Thesis lifecycle × health（STM-THS）

**transition table（ts01 §4.1 / ts03 §10.4）：**

```text
lifecycle: [*]→DRAFT；DRAFT→ACTIVE|ARCHIVED；ACTIVE→UNDER_REVIEW|INVALIDATED|ARCHIVED；
           UNDER_REVIEW→ACTIVE|INVALIDATED；INVALIDATED→ARCHIVED；ARCHIVED→[*]
health（与 lifecycle 正交，仅 ACTIVE/UNDER_REVIEW 下有效）：
           UNKNOWN→HEALTHY→WARNING→BROKEN（可回退）；evidence recovery 允许回退
```

| STM-THS-001 | lifecycle 全合法迁移逐一执行 | 每个合法迁移成功且状态正确；迁移记录 `actor/reason/timestamp/provenance`（thesis_events `STATUS_CHANGED`） |
| STM-THS-002 | lifecycle 非法迁移 → typed domain error | `ACTIVE→DRAFT`、`ARCHIVED→ACTIVE`、`INVALIDATED→UNDER_REVIEW` 等 → typed error（如 `INVALID_THESIS_TRANSITION`），无任何状态变更 |

## 10. CI 与执行策略（TS-08.9）

### 10.1 fresh test 语义（冻结）

> **每个 Milestone 验收前必须执行 fresh test：在干净的 CI 环境（全新容器、全新测试库、全新 parquet 目录）从零执行全量测试。** 不允许"增量通过"（只跑改动的测试）或复用上次的测试库状态。语义对应冻结规范 §48.13（"每个 Milestone 必须通过 fresh test"）与 §46 首句（"施工纪律是文字约束，必须由机器保障"）。

执行顺序（分层，由快到慢；**架构层最先**，任何一层失败即停止并返回失败报告）：

```text
① architecture（ARCH-*，61 个 ID）      —— 秒级，静态 + 轻量动态
② unit（STM-*/DQ-*/枚举/纯函数）          —— 秒级，无外部资源
③ golden（GOLD-*，64 个 ID）            —— 秒级，输入表直接注入
④ contract（CTR-*，64 个 ID）           —— 秒级，schema/golden 文件
⑤ integration（INT-*）                   —— 分钟级，测试库容器
⑥ acceptance（ACC-* 聚合）               —— 薄封装：校验 ①–⑤ 全绿 + 里程碑专项
```

### 10.2 分层执行与 PR 级策略

| 场景 | 执行范围 |
|---|---|
| 每个 PR（pre-merge） | ① 架构 + ② 单元 + ③ 黄金值（变更模块）+ ④ 契约（变更模块）——**架构层不可跳过** |
| 每个 Milestone 验收 | fresh test ①–⑥ 全量 |
| 版本发布（引擎变更） | ③ 黄金值全量回归 + ① 架构（黄金值回归失败 = 不得发布，ts06 E8） |
| 夜间/每周 | ①–⑥ 全量 + PIT 数据集全量 + 并发测试（409 竞争） |

CI 分层用 pytest marker（`@pytest.mark.arch` 等）+ `-m` 选择；`tests/architecture/` 目录默认纳入 pre-merge 必跑集合。

### 10.3 失败门禁（冻结）

| 层 | 失败语义 | 处理 |
|---|---|---|
| 架构（ARCH-*） | **任何架构违规 = 合入门槛**；不因"只是结构问题"降级 | PR 阻断；违规需修代码或走 ADR（冻结规范 §48.15） |
| 黄金值（GOLD-*） | 数值漂移 = 版本语义漂移（ts06 E6/E8） | 版本不得发布；必须升级 engine_version + ADR 或修 bug |
| 契约（CTR-*） | 契约破坏 | PR 阻断；改契约必须走 ADR + 同步 ts03/ts04/ts07 |
| 集成（INT-*） | 端到端断裂 | Milestone 阻断；允许 PR 级按标签跳过但必须显式理由 |
| 单元（STM/DQ） | 状态机/质量逻辑错误 | PR 阻断 |
| 验收（ACC-*） | Milestone 验收失败 | Milestone 不得宣称完成 |

### 10.4 覆盖率目标（建议）

| 范围 | 目标 | 说明 |
|---|---|---|
| 引擎计算核心（valuation/etf/portfolio/risk/fx/attention 的纯函数） | **分支覆盖 100%** | 黄金值 + 边界路径（FAIL/拒绝/缺口）全走 |
| 状态机服务层（thesis/valuation_run/trade_proposal/quota/workspace） | 分支覆盖 ≥95% | transition matrix 全覆盖 |
| Pydantic 校验层 | 行覆盖 100%（每条校验规则 ≥1 用例） | CTR-PYD 清单逐条 |
| 架构层 | 不适用行覆盖（规则断言本身即测试） | — |
| 全库（平均） | 行覆盖 ≥80% | 里程碑 gate |

> 覆盖率是**手段**不是目标：100% 覆盖不替代黄金值正确性；覆盖率不足但矩阵全绿时，先补矩阵缺口（黄金值/契约），再补分支。
