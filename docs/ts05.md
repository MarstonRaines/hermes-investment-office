## 执行摘要

**Provider 层是 Hermes Investment Office"事实与计算平面"（Investment Backend）的数据入口。** 它在架构中的位置由冻结规范第 2 章确立：Hermes 是控制平面（思考、编排、解释），Backend 是事实与计算平面（数据、状态、计算、审计）。Provider 层是事实平面最外层的一段"墙"——墙外是外部数据源（TuShare / AkShare / Yahoo / 巨潮 / FRED / SEC / 基金管理人），墙内是归一化事实（MarketBar / FinancialFact / NAV / FX / 持仓快照）与它们的 provenance 链。

TS-05 最重要的设计结论：

> **Provider 接口必须 Provider-independent：任何 TuShare / AkShare / Yahoo / 巨潮 的 response schema 都不得泄漏进业务层。业务层只认识 `instrument_id`、归一化字段与 `ProvenanceEnvelope`；Provider 的原始代码、原始字段名、原始单位、原始格式全部被挡在 Provider 适配器内部与 Raw Evidence Store 中。**

这一结论的直接理由是 TS-01 §5 与 TS-01 开放问题中反复出现的约束：**外部 Provider 的 SLA、接口、字段含义、限流与许可随时可能变化**（TuShare 积分调整、AkShare 爬虫接口波动、Yahoo 非官方接口被封）。只有把 Provider 契约做成"我们的契约"，才能保证 Provider 换掉时业务层零改动、历史 provenance 不失效。

### 三层分离（本文件的第二条主线）

```text
Provider 原始响应（JSON / CSV / PDF）
        │  ①  ProviderSymbol 映射（provider_symbols 表，时态）
        ▼
归一化事实（market_bar / financial_facts / etf_nav_observations / fx_observations …）
        │  ②  每行事实携带 provenance_id → ProvenanceRecord
        ▼
Provenance 链（source / provider / timestamps / quality / raw_hash / transform_version）
```

- **第 1 层 ProviderSymbol**：`provider_symbols` 是唯一的"外部代码 ↔ 内部身份"桥。任何 provider 调用都必须先 `resolve_instrument()` 把 provider symbol 映射为 `instrument_id`；**禁止把 provider symbol 当作内部主键**（冻结规范 §10、施工纪律第 9 条）。
- **第 2 层归一化事实**：只有归一化后的事实才允许进入 PG/Parquet 事实表，字段契约以 TS-02 为准（`market_bar_index` + `ohlcva/v1/`、`financial_facts`、`etf_nav_observations`、`etf_holding_snapshots`、`fx_observations`）。
- **第 3 层 ProvenanceRecord**：每个事实行通过 `provenance_id` 引用 `provenance_records`（TS-02 §4.1），记录来源、时点、质量、fallback 与 raw artifact 定位。**没有 provenance 的事实不允许落库**（TS-02 §4.1 关键规则）。

## 1. Provider 层定位与边界（TS-05.1）

### 1.1 在"事实与计算平面"中的位置

```text
Backend Scheduler (APScheduler)
        │  按 Trading Calendar 触发
        ▼
Job Worker（唯一允许调用 Provider 的执行者）
        │
        ▼
Data Gateway（编排层：resolve → fetch → fallback → normalize → persist）
        │
        ├── MarketDataProvider      → market_data 服务 → market_bar_index + ohlcva/v1/
        ├── FundamentalProvider     → fundamentals 服务 → financial_facts
        ├── FilingProvider          → events 服务 → documents/ + filing 元数据
        ├── ETFProvider             → etf 服务 → etf_nav_observations / etf_holding_snapshots
        ├── MacroProvider           → fx 服务 / market_data 服务 → fx_observations / 指数点位
        └── NewsProvider（v0.1 可选）→ events 服务 → 结构化事件记录
        │
        ▼
Raw Evidence Store（data/raw/… 原样保存）
```

三个必须被架构测试钉死的边界（冻结规范 §9 模块依赖方向、§46 架构测试）：

1. **providers 包只能被数据层（Data Gateway / 各数据服务）调用，业务引擎（valuation / portfolio / risk / etf 计算）不得反向依赖 providers**；
2. **Hermes 永不直接调用 provider**（§8）：Hermes 只能通过 MCP 触发 job 或查询已入库事实；
3. **Provider 层不跨出 Backend 进程**：所有网络 I/O 都在 Job Worker 内完成，API/MCP 层不做实时 provider 拉取。

### 1.2 Provider-independent 契约原则（冻结）

| 原则 | 强制内容 |
|---|---|
| P1 无 schema 泄漏 | 业务层/引擎层/API 层不得出现 TuShare/AkShare/Yahoo 字段名、单位、代码格式（如 `600519.SH`、`adj_close`、`ts_code`）；全部由适配器归一化 |
| P2 无 symbol 泄漏 | 所有跨层引用使用 `instrument_id`（UUID）；provider symbol 只存在于 `provider_symbols` 与 Raw 层 |
| P3 无时区泄漏 | 返回的时间戳统一 UTC（`TIMESTAMPTZ`），业务日期（trade_date/nav_date）单独 `DATE` 字段；A 股 Asia/Shanghai、美股 America/New_York 语义由适配器标注（冻结规范 §14.2） |
| P4 无单位泄漏 | 金额类归一化到 base_unit=CNY，保留四元组 `original_value / original_unit / value / unit`（冻结规范 §14.2、§47.2 Spike） |
| P5 质量必达 | 每个返回项必须携带 `ProvenanceEnvelope`（observed_at / retrieved_at / quality / fallback 信息） |
| P6 缺口即空 | "上游没有数据"（非交易日、未披露、停牌）返回空列表或显式 NULL 标记，**不抛异常**；"取数失败"（网络/超时/限流/鉴权）抛 typed `ProviderError`，触发 fallback（TS-02 §9.4 缺口语义） |

### 1.3 三层分离的工程理由

1. **Provider schema 变化不破坏业务层**：TuShare 调整 `daily` 字段、AkShare 接口改名，只需改对应适配器 + normalizer 版本，`market_bar_index` 契约不变；
2. **代码变化不破坏历史引用**：证券代码变更、Provider 格式变化（如 600519 → 600519.SH → 600519.SS）通过 `provider_symbols` 的 `valid_from/valid_to` 时态映射演进，历史事实的 `instrument_id` 不变（TS-01 §全局身份）；
3. **质量与来源可审计**：`quality_score` 只表示数据质量，不替代来源权威度（TS-01 §5）——冲突裁决先看 source authority，再看质量评分；
4. **可重解析**：Raw 层原样保存 + `transform_version` 记录，任何归一化逻辑升级后可对历史 raw artifact 重新解析（§7）。

## 2. Provider 接口契约（TS-05.2，冻结）

### 2.0 公共契约

以下类型为六个接口共享。**枚举与 TS-01 完全一致（source_kind、DataQualityStatus、QuotaStatus），此处是 Provider 层的 Pydantic 镜像，实际代码从领域共享模块导入，禁止出现两份定义。**

```python
"""providers/contracts/base.py —— 冻结：接口契约（TS-05 §2.0）"""
from abc import ABC, abstractmethod
from datetime import date, datetime
from decimal import Decimal
from enum import Enum
from typing import ClassVar
from uuid import UUID

from pydantic import BaseModel, Field


class DataQualityStatus(str, Enum):
    """镜像 TS-01 枚举，禁止改动。"""
    VERIFIED = 'VERIFIED'
    ACCEPTABLE = 'ACCEPTABLE'
    STALE = 'STALE'
    CONFLICT = 'CONFLICT'
    REJECTED = 'REJECTED'


class SourceKind(str, Enum):
    """镜像 TS-01 枚举；Provider 层产生的事实固定为 PROVIDER。"""
    OFFICIAL_FILING = 'OFFICIAL_FILING'
    EXCHANGE = 'EXCHANGE'
    PROVIDER = 'PROVIDER'
    HUMAN = 'HUMAN'
    HERMES = 'HERMES'
    DERIVED_ENGINE = 'DERIVED_ENGINE'


class QuotaStatus(str, Enum):
    """镜像 TS-01 枚举（TS-02 etf_metric_snapshots.quota_status 同源）。"""
    NOT_APPLICABLE = 'NOT_APPLICABLE'
    UNKNOWN = 'UNKNOWN'
    OPEN = 'OPEN'
    RESTRICTED = 'RESTRICTED'
    SUSPENDED = 'SUSPENDED'


class ProviderCapability(str, Enum):
    """能力声明：一个 provider 能提供哪些数据域（新增枚举，不与 TS-01 冲突）。"""
    CN_DAILY_QUOTE = 'CN_DAILY_QUOTE'        # A 股股票日行情
    CN_ETF_QUOTE = 'CN_ETF_QUOTE'            # A 股场内 ETF 行情（含 QDII ETF）
    ADJ_FACTOR = 'ADJ_FACTOR'                # 复权因子
    INDEX_QUOTE = 'INDEX_QUOTE'              # 指数点位（^GSPC / ^NDX / A 股指数）
    INDEX_WEIGHT = 'INDEX_WEIGHT'            # 指数成分与权重
    FINANCIAL_STATEMENTS = 'FINANCIAL_STATEMENTS'
    FUND_NAV = 'FUND_NAV'
    FUND_HOLDINGS = 'FUND_HOLDINGS'
    QUOTA_STATUS = 'QUOTA_STATUS'            # QDII 额度 / 限购状态
    FX_RATES = 'FX_RATES'
    INDEX_VALUATION = 'INDEX_VALUATION'      # 指数 PE/PB 历史
    MACRO_SERIES = 'MACRO_SERIES'
    FILINGS = 'FILINGS'                      # 公告 / 定期报告文档
    NEWS = 'NEWS'


class ProviderRole(str, Enum):
    PRIMARY = 'PRIMARY'          # 运营主源
    FALLBACK = 'FALLBACK'        # 备用源
    AUTHORITY = 'AUTHORITY'      # 权威冲突源（正式披露 / 交易所），冲突裁决时优先
    AUXILIARY = 'AUXILIARY'      # 辅助/验证用


class QualityTier(str, Enum):
    """Provider 质量分级（新增枚举；与 quality_score 互补，用于 Capability Matrix）。"""
    TIER_1 = 'TIER_1'            # 官方 / 交易所 / 正式披露：高权威，冲突裁决最高优先
    TIER_2 = 'TIER_2'            # 授权/规范化聚合接口（如 TuShare 标准化接口）
    TIER_3 = 'TIER_3'            # 免费聚合 / 爬虫（AkShare、Yahoo 非官方），需交叉验证
    TIER_4 = 'TIER_4'            # 未验证 / 一次性


class ProviderHealth(BaseModel):
    provider: str
    status: str                  # HEALTHY / DEGRADED / DOWN / UNKNOWN
    checked_at: datetime
    detail: dict[str, str] = Field(default_factory=dict)


class ProviderQualityReport(BaseModel):
    provider: str
    tier: QualityTier
    quality_score: Decimal = Field(ge=0, le=1)   # 近期数据质量评分（0-1），≠ 权威度
    last_success_at: datetime | None = None
    last_failure_at: datetime | None = None
    consecutive_failures: int = 0
    error_rate_1d: Decimal | None = None
    latency_p95_ms: int | None = None


class ProvenanceEnvelope(BaseModel):
    """与 TS-02 provenance_records 逐列对齐（映射见 TS-05 §2.0.4）。"""
    source_kind: SourceKind = SourceKind.PROVIDER
    source: str                                 # 来源名/数据集名（规范见各接口）
    provider: str                               # tushare / akshare / yahoo / cninfo / sec / web / internal
    source_uri: str | None = None
    source_record_id: str | None = None         # Provider 原始记录标识（规范见各接口）
    published_at: datetime | None = None        # 原始信息发布时点
    observed_at: datetime                       # 该数值代表的市场/事实时点
    retrieved_at: datetime                      # 系统取得数据时间
    as_of_date: date | None = None              # PIT 语义日期
    quality_score: Decimal = Field(ge=0, le=1)
    quality_status: DataQualityStatus
    quality_flags: list[str] = Field(default_factory=list)   # 缺失/异常/fallback/时间错配
    fallback_used: bool = False
    requested_provider: str | None = None       # fallback 时：请求的 primary
    fallback_reason: str | None = None          # PRIMARY_TIMEOUT / PRIMARY_RATE_LIMITED / ...
    raw_hash: str | None = None                 # sha256（见 §7）
    raw_object_key: str | None = None           # data/raw/... 相对路径
    ingestion_run_id: UUID | None = None        # 回溯 ingestion job
    transform_version: str                      # 规范化/计算版本


class ProviderError(Exception):
    """Provider 层 typed 错误基类。"""


class ProviderAuthError(ProviderError):
    """token 缺失/无效/积分不足（403）。"""


class ProviderRateLimited(ProviderError):
    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message)
        self.retry_after = retry_after


class ProviderTimeout(ProviderError):
    pass


class ProviderUnavailable(ProviderError):
    """网络不可达 / 上游 5xx / 超时（重试耗尽后）。"""


class ProviderDataError(ProviderError):
    """上游返回了但内容非法（字段缺失、单位异常、日期乱序）。"""


class ProviderConfigError(ProviderError):
    """配置缺失（token 未配置等），启动/健康检查时暴露。"""
```

#### 2.0.1 错误语义（冻结）

| 情形 | 处理 | 说明 |
|---|---|---|
| 上游明确无数据（非交易日、未披露、停牌无成交） | 返回空列表 / NULL 字段 | **合法缺口**，不是错误（TS-02 §9.4）；调用方按缺口语义处理 |
| 网络 / 超时 / 5xx | 抛 `ProviderTimeout` / `ProviderUnavailable` | 触发重试（§5.4），耗尽后触发 fallback（§5.1） |
| 限流 / 积分不足 | 抛 `ProviderRateLimited`（带 retry_after） | 按退避策略重试；多次限流可 fallback，`fallback_reason=RATE_LIMITED` |
| token 缺失 / 鉴权失败 | 抛 `ProviderAuthError` | 不重试、不 fallback，写 Audit + 告警 |
| 响应内容非法 | 抛 `ProviderDataError` | 记录 provider 原始响应到 raw 层后失败，供人工核查 |

### 2.1 MarketDataProvider — 行情数据

**数据范围**：A 股股票与 A 股场内 ETF 的日线 OHLCVA、复权因子、时点快照。v0.1 明确**不包含**分钟级 / tick 行情（冻结规范 §44 Non-goals）。

**频率限制假设**：日频 EOD 拉取（每 A 股交易日一次）；单次请求批量覆盖（建议按标的 × 日期范围批量，减少调用次数）。

**质量分级**：TuShare 实现默认 `TIER_2`，AkShare 默认 `TIER_3`；quality_score 由适配器按（缺口率、与权威源偏差、内部一致性）计算，验收前给出首个实测基线。

**provenance 生成规则**：`source_kind=PROVIDER`；`source=cn_daily_market` / `cn_etf_daily_market` / `cn_adj_factor`；`provider=tushare|akshare`；`observed_at=trade_date 15:00 Asia/Shanghai`（换算 UTC 存储）；`source_record_id=<provider_symbol>@<trade_date>`；`quality_flags` 可含 `ADJUSTED`（请求了复权）、`ZERO_VOLUME`、`GAP_DAY` 等。

```python
"""providers/contracts/market_data.py —— 冻结：MarketDataProvider（TS-05 §2.1）"""
class AdjustType(str, Enum):
```

### 2.2 FundamentalProvider — 财务事实

**数据范围**：三大报表（利润表 / 资产负债表 / 现金流量表）与财务指标，metric_code 使用 TS-02 §4.3 冻结清单（REVENUE / GROSS_PROFIT / OPERATING_INCOME / NET_INCOME / OPERATING_CASH_FLOW / CAPEX / FREE_CASH_FLOW / TOTAL_ASSETS / TOTAL_LIABILITIES / TOTAL_EQUITY / CASH / DEBT / SHARES_OUTSTANDING）。兼容中国 GAAP；避免固化任何 Provider schema（冻结规范 §16）。

**频率限制假设**：披露事件驱动 + 每日轮询（新披露出现后目标 ≤24h 入库，TS-01 §freshness）；单标的单期间为一次请求单位。

**质量分级**：TuShare 标准化接口 `TIER_2`（**积分门槛 2000+，SPIKE-PENDING**）、AkShare `TIER_3`；权威冲突源 = 巨潮/交易所正式披露（`AUTHORITY`）。

**provenance 生成规则**：`source=cn_financial_statements`；`source_record_id=<provider_symbol>@<period_end>@<published_at>`；`published_at` 必须保留（PIT 关键，TS-01 §5 财务事实 PIT 规则）；单位四元组必填（冻结规范 §14.2）。

```python
    original_value: Decimal | None = None  # 原始值（单位归一化四元组）
```

### 2.3 FilingProvider — 公告与文档

**数据范围**：A 股上市公司公告与定期报告（巨潮/交易所官方披露，`cninfo`）、SEC EDGAR 文档（`sec`，v0.1 仅当 QDII 底层穿透需要时启用）、基金管理人披露文档。返回**元数据 + PDF 下载**；PDF 进 Raw Evidence Store（`data/documents/`）。

**频率限制假设**：披露事件驱动 + 每日增量轮询；下载按需（文档可能较大，下载走 job 队列，不做实时）。

**质量分级**：巨潮/交易所/SEC 为 `TIER_1`（官方披露）；无 fallback 时该域数据缺失标记 `DATA_UNAVAILABLE`。

**provenance 生成规则**：`source_kind=OFFICIAL_FILING`（不是 PROVIDER——**公告是披露源本身**）；`source=cninfo_filings|sec_filings`；`provider=cninfo|sec|web`；`source_record_id` = Provider 原生文档 ID（巨潮 docId / SEC accession number），**原样保留、不重编**；`published_at` = 公告发布时间（交易所披露时点）。

### 2.4 ETFProvider — ETF / 基金披露数据

**数据范围**：基金 NAV 观测、披露持仓快照、QDII 额度状态。覆盖普通 A 股 ETF 与 QDII ETF（冻结规范 §12.3：基金公司季报 / AkShare 基金接口）。

**频率限制假设**：NAV 日更（T+1 披露，`nav_date` 与 `published_at` 并存，TS-02 §4.4）；持仓季报/半年报/年报披露日事件驱动；额度事件驱动（公告出现才更新，**禁止轮询推断**）。

**质量分级**：基金管理人正式披露 `TIER_1`（AUTHORITY）；AkShare 基金聚合接口 `TIER_3`（FALLBACK）。

**provenance 生成规则**：NAV `source=cn_fund_nav`、`source_record_id=<provider_symbol>@<nav_date>`；持仓 `source=cn_fund_holdings`、`source_record_id=<provider_symbol>@<report_period>@<source>`；额度 `source=cn_fund_quota_announcement`、`source_record_id=<provider_symbol>@<announcement_date>`。**额度是事件状态，必须来自公告 provenance，禁止从溢价率推断**（TS-01 §生命周期、TS-02 §4.6）。

### 2.5 MacroProvider — 指数 / FX / 宏观

**数据范围**：
- 指数点位：美股指数（`^GSPC` / `^NDX`，仅 INDEX 标的，**不抓 SPY/VOO/QQQ**——冻结规范 §12.3）与 A 股指数；
- FX：USD/CNY（仅 QDII 分析使用，TS-01 §组合币种）；
- 指数估值：Index PE/PB 历史（`index_valuation`，供 ETF Engine 历史分位计算，TS-02 §4.6 `index_pe/index_pb`）；
- 宏观序列：FRED（利率、CPI 等，v0.1 可选支持）。

**频率限制假设**：指数点位 EOD（每美股交易日一次）；FX 按 QDII 分析批次（每交易日 1 次或盘中按需）；指数估值定期（周/月）或事件驱动；宏观按发布日历。

### 2.7 接口级一致性规则汇总（冻结）

| 规则 | 范围 | 强制方式 |
|---|---|---|
| 所有返回项携带 `ProvenanceEnvelope` | 六接口全部 | Pydantic 类型强制 + 架构测试 |
| 空结果 = 合法缺口，不抛异常 | 全部 | 契约文档 + 单测 |
| 取数失败抛 typed `ProviderError` | 全部 | 异常层级 |
| 时间戳 UTC + 业务日期 DATE | 全部 | normalizer 统一时区处理 |
| 单位四元组（original/value） | FundamentalProvider | schema 字段必填 |
| `instrument_id` 由调用方解析后传入，接口内不再出现 provider symbol 主键 | 全部 | 签名类型 `UUID` |
| 幂等：同参数重复调用返回相同事实集合 | get 型接口 | 适配器无副作用 + job upsert-by-supersede |
| 限流/积分信息不进业务字段 | 全部 | `ProviderRateLimited` 异常携带，写 audit |

### 3.2 注册机制（冻结）

采用 **声明式注册表 + 工厂 + 依赖注入** 三层：

```python
"""providers/registry.py —— 冻结：注册表（TS-05 §3.2）"""
class ProviderRegistry:
    """进程内单例。注册内容必须与 provider-capability.md 一致（架构测试校验）。"""

    def __init__(self) -> None:
        self._impls: dict[str, type[BaseProvider]] = {}

    def register(self, provider_cls: type[BaseProvider]) -> None:
        name = provider_cls.provider_name
        if name in self._impls:
            raise ProviderConfigError(f'duplicate provider: {name}')
        self._impls[name] = provider_cls

    def get(self, provider_name: str) -> type[BaseProvider]: ...
    def all(self) -> dict[str, type[BaseProvider]]: ...

    def providers_for(self, capability: ProviderCapability) -> list[type[BaseProvider]]:
        """实现该能力的所有 provider（按 matrix 角色排序）。"""

    def primary_for(self, capability: ProviderCapability) -> type[BaseProvider]: ...
    def fallback_chain(self, capability: ProviderCapability) -> list[type[BaseProvider]]:
        """primary → secondary → ...（由 provider-capability.yaml 定义，见 §4）。"""
```

- **注册**：每个实现模块底部 `registry.register(TuShareMarketDataProvider)`（或装饰器 `@register_provider`），应用启动时收集注册；**注册即声明能力**（`capabilities` 类属性）。
- **工厂**：`create_provider(name, settings)` 从配置层读取该 provider 的 token/超时/限流参数并注入实现（见 §3.5），返回配置完成的实例；**配置不进代码**。
- **DI**：FastAPI / 服务层通过 `DataGateway` 获取 provider 实例；业务引擎只依赖接口类型与 `instrument_id`，不 import 任何具体实现（架构测试：`valuation/portfolio/risk` 禁止 import `providers.*`）。

## 5. Fallback 机制（TS-05.5，冻结）

### 5.1 Fallback 链定义（冻结）

每个数据域在 `provider-capability.yaml` 中定义 **fallback 链**（primary → secondary → 终态）。终态只有两种：`DATA_UNAVAILABLE`（确实没有）或 `CONFLICT`（有但不可信/多源打架）：

```text
Primary requested（如 tushare）
      │
      ├── valid ────────────────────► accept（fallback_used=false）
      │
      └── unavailable/invalid（超时/限流耗尽/数据非法）
                   │
                   ▼
              fallback policy（§5.2）
                   │
                   ▼
              Secondary（如 akshare）
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
       valid               invalid
         │                   │
         ▼                   ▼
  fallback_used=true    DATA_UNAVAILABLE
  quality 调整 + flag       或 CONFLICT
```

初始 fallback 链（冻结规范 §12 落实，spike 后修订需 ADR）：

| 数据域 | 链 |
|---|---|
| CN_DAILY_QUOTE / CN_ETF_QUOTE | tushare → akshare → DATA_UNAVAILABLE |
| ADJ_FACTOR | tushare → akshare → corporate_actions 人工校准 → CONFLICT |
| FINANCIAL_STATEMENTS | tushare → akshare → DATA_UNAVAILABLE（权威冲突源 = 巨潮/交易所正式披露） |
| INDEX_WEIGHT | tushare → akshare → DATA_UNAVAILABLE（spike 决定 v0.1 是否必需） |
| US_INDEX_QUOTE | yahoo → 备用源（SPIKE-PENDING）→ DATA_UNAVAILABLE |
| FUND_NAV | fund_official → akshare → DATA_UNAVAILABLE |
| FUND_HOLDINGS | fund_official → akshare → DATA_UNAVAILABLE |
| QUOTA_STATUS | fund_official → verified_aggregator → **UNKNOWN**（禁止假装 OPEN，TS-01 §freshness） |

### 5.2 Fallback 决策与记录（对齐 TS-01 §5）

**Fallback 决策只发生在 Data Gateway（编排层）**，Provider 实现内部**绝不自行换源**——这是"禁止静默 fallback"的第一道架构强制点。

```python
"""providers/gateway.py —— 冻结：DataGateway fallback 决策（TS-05 §5.2）"""
class FallbackDecision(BaseModel):
    requested_provider: str          # primary
    actual_provider: str             # 实际取数的 provider
    fallback_used: bool
    fallback_reason: str | None      # PRIMARY_TIMEOUT / PRIMARY_RATE_LIMITED / PRIMARY_DATA_ERROR / PRIMARY_UNAVAILABLE / NO_FALLBACK
    attempts: list[str]              # [tushare, akshare]
    quality_adjustment: Decimal      # 质量衰减系数（见下）


FALLBACK_QUALITY_ADJUSTMENT = {
    'PRIMARY_TIMEOUT': Decimal('0.95'),
    'PRIMARY_RATE_LIMITED': Decimal('0.93'),
    'PRIMARY_DATA_ERROR': Decimal('0.90'),
    'PRIMARY_UNAVAILABLE': Decimal('0.95'),
}

class DataGateway:
    """resolve → fetch（带 fallback）→ normalize → persist + provenance + audit。"""

    async def fetch_with_fallback(
        self,
        capability: ProviderCapability,
        fetcher,                       # 具体取数函数（由调用方注入）
        instrument_id: UUID,
    ):
        chain = self.registry.fallback_chain(capability)
        decision = FallbackDecision(requested_provider=chain[0].provider_name,
                                    actual_provider=chain[0].provider_name,
                                    fallback_used=False,
                                    attempts=[])
        for idx, provider_cls in enumerate(chain):
            provider = self.factory(provider_cls)
            decision.attempts.append(provider.provider_name)
            try:
                result = await fetcher(provider)
                return result, decision          # 成功即返回
            except ProviderRateLimited as e:
                # 限流：按退避重试（§5.4），多次限流后进入下一个 provider
                if idx == len(chain) - 1:
                    decision.fallback_used = True
                    decision.actual_provider = provider.provider_name
                    decision.fallback_reason = 'RATE_LIMITED'
                    raise DataUnavailable(capability, decision) from e
                continue
            except ProviderError as e:
                decision.fallback_used = True
                decision.fallback_reason = ...   # 映射原因
                if idx == len(chain) - 1:
                    raise DataUnavailable(capability, decision) from e
                continue
        raise DataUnavailable(capability, decision)
```

**记录契约（TS-01 §5 fallback 决策记录，落库映射见 §2.0.4）**：

```json
{
  "requested_provider": "tushare",
  "actual_provider": "akshare",
  "fallback_used": true,
  "fallback_reason": "PRIMARY_TIMEOUT",
  "quality_score": 0.91
}
```

- `ProvenanceEnvelope.quality_score` 在 fallback 时按 `quality_adjustment` 衰减（如 primary 源质量基线 0.96 → fallback 后 0.91），并在 `quality_flags` 追加 `FALLBACK_USED`；
- 完整 `requested_provider / actual_provider / fallback_reason / attempts` 写入 **audit_events**（action=`PROVIDER_FALLBACK`，payload 完整记录）与 provenance quality_flags；
- 终态 `DATA_UNAVAILABLE` / `CONFLICT` 也是显式结果：写入 provenance（quality_status=STALE/REJECTED 或标记缺口），**不允许假装数据存在**。

### 5.3 禁止 silent fallback 的架构强制点（冻结）

1. **Provider 实现内部禁止换源**：每个 Provider 只调用自己的上游；换源逻辑只存在于 Data Gateway（§5.2）；
2. **服务层拦截**：所有数据服务（market_data / fundamentals / etf / fx）必须经由 DataGateway 取数，禁止绕过 gateway 直连 provider；
3. **audit + provenance 双写**：fallback 发生时 provenance.quality_flags 含 `FALLBACK_USED`、fallback_used=true，audit_events 必有一行 `PROVIDER_FALLBACK`（与业务事务同提交或 outbox，TS-02 §12）；
4. **MCP 响应可见**：TS-01 统一响应包络的 `quality` 与 `provenance` 字段必须携带 fallback 信息（Hermes 可查询数据 provenance，冻结规范 §13）；
5. **架构测试（TS-08 细化）**：
   - mock primary 抛 `ProviderTimeout` → 断言 fallback 记录存在、audit 行存在、quality_flags 含 FALLBACK 标记；
   - 断言 providers 包内无"调用其他 provider"的 import（静态检查）；
   - 断言所有数据服务 import 路径经过 gateway；
6. **禁止场景示例**：TuShare 失败 → 偷偷改 AkShare → 对上层仍声称"行情正常"（冻结规范 §13）——一旦发现即架构违规。

### 5.4 重试与退避策略（冻结）

| 参数 | 默认 | 说明 |
|---|---|---|
| 幂等性 | get 型接口天然幂等；同步 job 落库 upsert-by-supersede | 重试不会产生重复事实 |
| 超时 | connect 10s / read 20s（可配置） | 超时 = 一次尝试失败 |
| 重试次数 | max_retries=2~3（配置） | 每次失败递增 |
| 退避 | `base * 2^n + jitter`，base 默认 1.0s | 防雪崩 |
| 限流响应 | 429 / retry_after 优先尊重 | 见下 |
| 取消 | 重试间检查 job 取消信号 | Job 被 kill 时立即退出 |

- **限流（429 / TuShare 积分不足 403）**：抛 `ProviderRateLimited` → 若 `retry_after` 存在则等待后重试；连续限流达到阈值（如 3 次）→ 视为该 provider 本轮不可用 → 进入 fallback 链，`fallback_reason=RATE_LIMITED`；
- **重试语义不改变 observed_at**：重试只影响 `retrieved_at`（以最终成功拉取时点为准）；provenance 忠实记录"何时取得"；
- **不重试的错误**：`ProviderAuthError`（token 问题重试无用）、`ProviderConfigError`、`ProviderDataError`（内容非法，重试大概率同样非法）——直接失败 + audit + 告警；
- **Job 级兜底**：重试与 fallback 全部失败 → job 标记 FAILED 并记录 error（冻结规范 §35.4），**不可静默吞掉**；下一调度周期重试，避免无限循环（job 幂等去重）。

### 5.5 多源交叉验证（冻结）

**场景**：正式披露 vs 聚合器冲突时 **source authority 优先**（TS-01 §5），quality_score 不能凌驾于权威度：

```text
Company official filing（巨潮/交易所）: Revenue = X
aggregator（TuShare/AkShare）       : Revenue = Y

同一报告口径下：official wins（AUTHORITY 优先）
系统不删除 Y：保留为 quality_status=CONFLICT，superseded_by=official observation
无法判定：CONFLICT，decision-sensitive 引擎默认拒绝使用（TS-02 §4.1）
```

交叉验证策略（按数据域配置）：

| 策略 | 数据域 | 行为 |
|---|---|---|
| REQUIRED（必须） | FINANCIAL_STATEMENTS、FUND_NAV、QUOTA_STATUS | 聚合源数据与权威源比对；不一致 → CONFLICT 标记，不静默采用 |
| ADVISORY（建议） | CN_DAILY_QUOTE、CN_ETF_QUOTE | 两个聚合源偏差超阈值（如收盘价 > 0.1%）→ 打 `CROSS_SOURCE_DEVIATION` flag，不阻塞 |
| NONE | MACRO_SERIES 等单一权威源 | 无交叉 |

冲突解决顺序（冻结，TS-01 §5）：

```text
Source authority → Point-in-time validity → Publication/version recency
→ Schema/unit validation → Provider quality → Manual adjudication if unresolved
```

> 多源交叉验证的比对结果与原始值都必须保留（append-only），供审计与后续重判。

## 6. 限流与配额管理（TS-05.6）

### 6.1 TuShare 积分制应对策略（冻结 + SPIKE-PENDING）

TuShare 为积分制（冻结规范 §12.1）：**关键接口（财务三大报表、复权因子、指数成分/权重）有积分门槛**，具体可用范围必须在 M0.5 Spike 实测（§9）。spike 前以下为**预期档位（假设，不冻结）**：

| TuShare 接口 | 数据 | 预期最低积分 | 状态 |
|---|---|---|---|
| `stock_basic` / `trade_cal` | 基础信息/交易日历 | 低（约 120-200 档） | SPIKE-PENDING |
| `daily` | A 股日线 | 低-中 | SPIKE-PENDING |
| `daily_basic` | 每日指标（PE/PB） | 中（200 档） | SPIKE-PENDING |
| `adj_factor` | 复权因子 | **高（约 2000）** | SPIKE-PENDING |
| `income` / `balancesheet` / `cashflow` | 三大报表 | **高（约 2000）** | SPIKE-PENDING |
| `fina_indicator` | 财务指标 | **高（约 2000）** | SPIKE-PENDING |
| `index_daily` / `index_dailybasic` | 指数行情 | 高 | SPIKE-PENDING |
| `index_weight` | 指数成分权重 | **高（约 2000）** | SPIKE-PENDING |
| `fund_basic` / `fund_nav` | 基金基础/NAV | 高 | SPIKE-PENDING |

**应对策略（无论实测档位如何都生效）**：

1. **缓存优先**：所有标准化事实落 PG/Parquet 后即为缓存；同步 job 只拉增量（新交易日/新披露），**禁止重复拉取已入库区间**（幂等 upsert-by-supersede）；
2. **批量抓取窗口**：EOD 后单次窗口批量拉取（先核心持仓/观察池，后扩展池），减少接口调用次数；大历史区间（如首次全量）分片拉取并记录分片 checkpoint；
3. **优先级队列**：`universe` 按重要性分级（持仓 > 观察池 > 扩展），积分/额度紧张时按优先级保核心标的；
4. **积分档位感知**：`providers.yaml` 的 `score` 字段声明当前档位；启动校验调用方请求的接口是否在档位内，超出 → 显式 `ProviderRateLimited`（不进 silent fallback 陷阱）；
5. **Spike 实测要求（§9）**：实测确认"当前积分下哪些接口可用、调用频率上限"，写入 matrix，作为同步 job 调度参数的依据；
6. **应急路径**：TuShare 积分不足/停服 → fallback 到 AkShare（记录 fallback）；二者都不可用 → DATA_UNAVAILABLE + 告警 + daily_context freshness 降级（§8/冻结规范 §36）。

### 6.2 通用限流框架（冻结）

```python
"""providers/rate_limiter.py —— 冻结：令牌桶（TS-05 §6.2）"""
class TokenBucket:
    def __init__(self, qps: float, burst: int) -> None: ...
    async def acquire(self) -> None: ...        # 容量不足时等待

class ProviderRateLimiter:
    """每个 provider 一个令牌桶 + 日额度计数。配置见 providers.yaml §3.5。"""
    def __init__(self, provider_name: str, qps: float, burst: int, daily_quota: int) -> None: ...
    async def acquire(self) -> None: ...
    def remaining_today(self) -> int: ...
```

- **按 provider 的 QPS / 日额度配置**（§3.5 `rate_limit` 节），全部来自配置层；
- **job 调度错峰**：Backend Scheduler 按 provider 分时段排程（如 TuShare 行情 job 收盘后 15:30、AkShare 轮询 job 错开 30 分钟），避免多个 job 同时打爆同一 provider（§8.3 排程建议）；
- **日额度耗尽**：剩余任务标记 `DEFERRED`，下一调度窗口继续（job 幂等，不丢数据）；`remaining_today()` 供 scheduler 查询做排程决策；
- **单机单进程限流即可满足 v0.1**（模块化单体，冻结规范 §7；Redis 非必需）。

### 6.3 数据新鲜度与抓取频率建议（冻结建议值，可在 Data Quality Policy 参数化）

| 数据 | 抓取频率 | 触发 | 新鲜度目标（TS-01 §5 对齐） |
|---|---|---|---|
| A 股/ETF 日行情 | EOD 每交易日一次 | trading_calendar（CN） | 收盘后 ≤2h 入库；落后 >1 session → WARN |
| 美股指数点位 | EOD 每美股交易日一次 | trading_calendar（US） | 收盘后 ≤2h |

## 7. 原始数据保存（Raw Evidence Store 契约，TS-05.7）

### 7.1 目录结构（冻结）

冻结规范 §8.3 / §14.1：RAW 层原则 = **尽量原样保存、可重复解析、可追溯**。

```text
data/
├── raw/
│   ├── tushare/
│   │   └── 2026-08-21/
│   │       └── market_sync_job/
│   │           ├── daily_513100.SH_2026-08-21.json
│   │           └── daily_600519.SH_2026-08-21.json
│   ├── akshare/
│   │   └── 2026-08-21/
│   │       └── fundamental_sync_job/
│   │           └── fin_600519.SH_2026H1.json
│   ├── yahoo/
│   │   └── 2026-08-20/
│   │       └── macro_sync_job/
│   │           └── quote_^NDX_2026-08-20.json
│   ├── cninfo/
│   │   └── 2026-08-18/
│   │       └── filing_sync_job/
│   │           └── 1200001234.json        # 公告元数据
│   └── fred/
│       └── 2026-08/
│           └── macro_sync_job/
│               └── DEXCHUS_2026-08.json
├── parquet/            # ohlcva/v1/、financial_history/v1/、etf_holdings/v1/（TS-04）
└── documents/          # 财报 PDF、公告 PDF、SEC Filing
    ├── cninfo/2026/1200001234.pdf
    └── sec/2026/0000320193-26-000123.pdf
```

- 路径语义：`data/raw/{provider}/{yyyy-mm-dd}/{job_name}/{payload}`；文件名为**人类可读的检索标签**（含 provider symbol 与日期），但**不参与业务主键**（主键仍是 provenance_id / fact id）；
- **原样保存**：Provider 返回的原始 JSON/CSV 字节级写入（不转换、不截断、不重排字段）；网络传输的 content 直接落盘；
- 一个"拉取单元"（一次接口调用的完整响应）对应一个 raw artifact。

### 7.2 raw_hash / raw_object_key 与 provenance 关联（冻结）

```text
raw artifact 落盘
   ↓ sha256(content bytes)
raw_hash（provenance_records.raw_hash）
raw_object_key = 相对 data/ 的路径（provenance_records.raw_object_key）
   ↓
同一 artifact 归一化出的每条事实共用同一 raw_hash/raw_object_key
```

- **raw_hash = sha256(原始字节)**：内容指纹，用于重解析校验、去重、防篡改；
- **raw_object_key**：如 `raw/tushare/2026-08-21/market_sync_job/daily_513100.SH_2026-08-21.json`；`provenance_records.raw_object_key` 存相对 `data/` 的路径；
- 一个 artifact → N 条事实（如一次批量行情响应 → 多条 bar）：**每条事实的 provenance 都引用同一 raw_hash/raw_object_key**；
- 文档类（PDF）走 `data/documents/`，同样生成 hash，`evidence_items.content_hash` / `FilingMeta.content_hash` 引用（TS-02 §5.7）。

### 7.3 重解析能力（冻结）

```text
RAW（原样字节）
   ↓ normalizer（transform_version=market-normalizer/0.1.0）
NORMALIZED（fact + provenance）
   ↓ 升级后
重新解析：读 raw artifact → 新版本 normalizer → upsert-by-supersede（旧行 superseded，不覆盖）
```

- **可重复解析**：normalizer 的唯一输入是 raw artifact（+ 配置），不依赖网络、不依赖 Provider 当前 schema；只要 artifact 在，任何版本 normalizer 都能重跑；
- **可追溯**：`transform_version` 记录"这条事实是用哪个版本规约出来的"；重解析产生新 observation（supersede 旧值），历史 provenance 链保留；
- **保留**：`data/raw` 与 `data/documents` 永久保留，纳入备份策略（冻结规范 §41）；仅缓存层可 TTL 删除（TS-01 §保留）。

## 8. 与 Job 系统的集成（TS-05.8）

### 8.1 Provider 调用只发生在 Backend Job Worker（冻结）

```text
Hermes ──MCP──► Backend API ──► 创建/查询 job_runs（不触达 provider）
                                          │
Backend Scheduler（APScheduler，按 Trading Calendar）
                                          ▼
                                    Job Worker ◄── 唯一允许调用 Provider 的执行者
                                          │
                                          ▼
                               Data Gateway → Provider → Raw → Normalize → PG/Parquet
```

- **Hermes 永不直接调用 provider**：Hermes 侧没有任何 provider 客户端；MCP 工具清单（冻结规范 §32）中没有 provider 类工具；
- 架构强制：`mcp/` 与 `api/` 模块禁止 import `providers.*`（架构测试）；Hermes 物理上无法触达 backend 代码与数据目录（§4.4 物理隔离）；
- Hermes 唯一的"数据动作"是**触发同步 job**（幂等）与**查询已入库事实**。

### 8.2 `sync_market_data` 类 MCP 工具（幂等触发，冻结）

```text
MCP tool: sync_market_data(universe: list[instrument_id] | ALL, start: date, end: date)
        │
        ▼
Backend: 规范化参数（resolve 到 job 参数指纹）
        │
        ▼
job_runs 表：
  - 同参数指纹（universe+范围+类型）存在 RUNNING/SUCCEEDED 且覆盖所需区间 → 返回既有 job（幂等，不重复创建）
  - 否则创建新 job（status=PENDING）→ 由 Scheduler/Worker 异步执行
        │
        ▼
返回 { job_run_id, status: "PENDING" | "ALREADY_RUNNING" | "SUCCEEDED", coverage }
```

- **幂等三要素**：参数指纹去重 + 覆盖区间检查 + upsert-by-supersede 落库——重复触发不产生重复数据、不重复拉取；
- **触发 ≠ 同步完成**：工具只负责入队；Hermes 通过 `get_job_status()` 查询进度（冻结规范 §32.8），**禁止在 MCP 层等待 provider 拉取**；
- 对应工具组：`sync_market_data` / `sync_fundamentals`（冻结规范 §32.1/§32.2）；ETF/FX/宏观同步的 MCP 触发工具按需扩展，同样只触发 job。

### 8.3 Job 类型与同步流程（冻结）

| Job（job_runs.job_name） | job_type | 调用的 Provider 接口 | 产出 |
|---|---|---|---|
| `market_sync_job` | SYNC_JOB | MarketDataProvider.get_price_history / get_market_snapshot / get_adj_factors | market_bar_index + ohlcva/v1/ + corporate_actions 因子输入 |
| `fundamental_sync_job` | SYNC_JOB | FundamentalProvider.get_financial_facts / get_financial_history / get_latest_filings | financial_facts + financial_history/v1/ |
| `filing_sync_job` | SYNC_JOB | FilingProvider.get_filings / download_document | filing 元数据 + data/documents/ |
| `etf_sync_job` | SYNC_JOB | ETFProvider.get_nav_history / get_holding_snapshots / get_quota_status | etf_nav_observations + etf_holding_snapshots + quota 状态 |
| `macro_sync_job` | SYNC_JOB | MacroProvider.get_index_history / get_fx_rates / get_index_valuation | 指数点位 + fx_observations + index valuation |
| `valuation_job` / `risk_job` / `brief_generation_job` | COMPUTE_JOB / BRIEF_JOB | 不调用 provider（消费事实） | 引擎产出 |

**同步 job 内部流程（冻结）**：

```text
1. 取 universe（持仓 + 观察池 instrument_id 列表）
2. resolve_instrument：instrument_id → 各 provider 的 symbol（provider_symbols，valid_to IS NULL）
3. 计算增量区间（上次成功 checkpoint → 现在）
4. 经 DataGateway 拉取（限流 + fallback，§5/§6）
5. raw artifact 落盘（§7）
6. normalize（transform_version）→ 事实 + ProvenanceEnvelope
7. 同事务写入：facts + provenance_records + market_bar_index 等（TS-02 §12 事务边界）
8. audit_events + job_runs 状态更新（SUCCEEDED/FAILED + error）
```

**失败处理**：job 失败记录 error 并告警、不阻塞其他独立 job、不静默吞掉（冻结规范 §35.4）；同步失败导致 daily_context 无法生成时按 Freshness Contract 处理（§36：data_freshness != OK 时 Hermes 禁止生成建议）。

### 9.2 输出与回流流程（冻结）

```text
M0.5 Spike 执行
   ↓
provider-capability-report.md（docs/data-contracts/）
   ├── 每项验证的实测证据（日期、样本、成功率、字段样例）
   ├── 与冻结策略的冲突点清单（如 TuShare 积分不足某接口）
   └── 建议的 matrix 修订
   ↓
更新 config/provider-capability.yaml + 生成 provider-capability.md（§4）
   ↓
新增 ADR（或在 ADR-002-provider-strategy 追加修订）：修改原因、影响范围、迁移方案
   ↓
架构测试：YAML ↔ 代码注册表 ↔ 实现 三方一致（§3.2/§4.3）
```

**回流禁止事项（冻结规范 §47）**：spike 报告与实现脱节——"报告写一份、实现按另一套"是施工纪律违规；若实测与冻结策略冲突（如 TuShare 积分不足、某接口不可用），**必须**通过 ADR 更新 §12 数据源策略与 provider-capability.md。
